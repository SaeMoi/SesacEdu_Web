# 결제 · 가상PG 테스트 가이드

결제 흐름(장바구니 → 결제 → 가상PG → 결제내역/영수증)을 로컬에서 시험할 때 쓰는 값과 기대 결과입니다.
실제 결제는 일어나지 않습니다. 승인/거절은 서버 안의 가상PG(`POST /virtualPG/buy/confirm`)가 아래 규칙으로 정합니다.

## 흐름 요약

| 단계 | API | 성공 응답 |
|---|---|---|
| 결제 화면 | `GET /mypage/buy` | 200 `CHECKOUT_ITEMS_FOUND` (강의, 쿠폰 목록, 합계) |
| 쿠폰 미리보기 | `GET /mypage/buy/cpn?courseIds=..&couponId=..` | 200 `COUPON_APPLIED` |
| 주문 생성 | `POST /mypage/buy` | 201 `ORDER_CREATED` (`orderId`) / 0원이면 `ORDER_COMPLETED` |
| 결제 | `POST /payment` `{ orderId, card }` 또는 `{ orderId, transfer }` | 200 `PAYMENT_COMPLETED` |
| 결제내역 | `GET /mypage/buy/history` | 200 `ORDER_HISTORY_FOUND` |
| 결제 상세·영수증 | `GET /mypage/buy/history/{orderId}` | 200 `ORDER_DETAIL_FOUND` |

결제가 끝나면 화면은 `/mypage/buy/complete?orderId=N` 으로 이동하고 "결제가 완료되었습니다" 카드를 보여 줍니다 (새로고침해도 상세 API로 다시 그립니다).

## 1. 카드 결제

### 입력 형식 (틀리면 `400 INVALID_INPUT`, 가상PG까지 가지 않음)

| 항목 | 규칙 |
|---|---|
| 카드번호 | 숫자 14~16자리 (공백, `-` 는 무시) |
| 유효기간 | `MM/YY` (예: `12/29`) |
| CVC | 숫자 정확히 3자리 (아무 값이나 가능, 예: `123`) |
| 할부 | `0`(일시불) 또는 `2`~`12` |

### 테스트 카드번호와 결과

형식이 맞으면 가상PG가 위에서부터 차례로 검사합니다.

| 카드번호 | 유효기간 | 결과 | 응답 |
|---|---|---|---|
| `4111 1111 1111 1111` | 미래 (예: `12/29`) | **승인** | 200 `PAYMENT_COMPLETED` |
| `5555 5555 5555 4444` | 미래 | **승인** | 200 `PAYMENT_COMPLETED` |
| `4111 1111 1111 1112` | 미래 | 거절: 카드번호 오류 (Luhn 검사 실패) | 402 `PAYMENT_DECLINED`, `reason: INVALID_CARD` |
| `4111 1111 1111 1111` | 지난 달 이전 (예: `01/20`) | 거절: 유효기간 만료 | 402, `reason: EXPIRED_CARD` |
| `4111 1111 1107 0002` | 미래 | 거절: 잔액 부족 | 402, `reason: INSUFFICIENT_BALANCE` |
| `4111 1111 1106 0003` | 미래 | 거절: 한도 초과 | 402, `reason: LIMIT_EXCEEDED` |
| `4111 1111 1100 0009` | 미래 | 가상PG가 15초 늦게 응답 → 서버 타임아웃(10초) | 502 `PG_UNAVAILABLE` |

- 카드번호는 **Luhn 검사**를 통과해야 합니다. 임의 숫자 16자리는 대부분 `INVALID_CARD` 입니다. 위 번호를 쓰세요.
- 끝 4자리 규칙: `0002` = 잔액 부족, `0003` = 한도 초과, `0009` = 지연. 새 번호를 만들 때도 Luhn을 맞춰야 합니다.
- `0009` 의 경우 화면은 실패지만, 가상PG는 뒤늦게 **승인으로 CSV에 기록**합니다 (타임아웃 테스트용). 주문은 `pending` 으로 남아 다시 결제할 수 있습니다.

## 2. 계좌이체

### 입력 형식 (틀리면 `400 INVALID_INPUT`)

| 항목 | 규칙 |
|---|---|
| 은행 코드 | 숫자 3자리 |
| 계좌번호 | 숫자 10~14자리 |
| 예금주 | 1~20자 (아무 이름이나 가능, 예: `김새싹`) |

### 사용 가능한 은행 코드

목록에 없는 3자리 코드는 형식은 통과하지만 가상PG가 `INVALID_ACCOUNT` 로 거절합니다.

| 코드 | 은행 | 코드 | 은행 | 코드 | 은행 |
|---|---|---|---|---|---|
| 002 | 산업 | 027 | 씨티 | 045 | 새마을금고 |
| 003 | 기업 | 031 | 대구 | 048 | 신협 |
| 004 | 국민 | 032 | 부산 | 071 | 우체국 |
| 007 | 수협 | 034 | 광주 | 081 | 하나 |
| 011 | 농협 | 035 | 제주 | 088 | 신한 |
| 020 | 우리 | 037 | 전북 | 089 | 케이뱅크 |
| 023 | SC제일 | 039 | 경남 | 090 | 카카오뱅크 |
| | | | | 092 | 토스뱅크 |

### 테스트 값과 결과

| 은행 코드 | 계좌번호 | 예금주 | 결과 | 응답 |
|---|---|---|---|---|
| `004` | `12345678901234` | `김새싹` | **승인** | 200 `PAYMENT_COMPLETED` |
| `004` | `12345678900002` (끝 `0002`) | `김새싹` | 거절: 잔액 부족 | 402, `reason: INSUFFICIENT_BALANCE` |
| `999` | `12345678901234` | `김새싹` | 거절: 없는 은행 | 402, `reason: INVALID_ACCOUNT` |
| `04` | `12345678901234` | `김새싹` | 형식 오류 | 400 `INVALID_INPUT` |

- 계좌번호는 Luhn 검사가 없습니다. 끝 4자리 `0002` 만 특별 취급합니다 (`0003`, `0009` 는 카드에만 해당, 계좌는 승인).
- 예금주는 실제 이름과 대조하지 않습니다.

## 3. 공통 규칙

- 결제 금액이 **1,000,000원 초과**이면 카드/계좌 모두 402 `LIMIT_EXCEEDED`.
- 거절(402)이어도 주문은 `pending` 으로 남고 아무것도 차감되지 않습니다. 같은 주문으로 다시 결제할 수 있습니다.
- 이미 결제된 주문을 다시 결제하면 409 `ALREADY_PAID`. 남의 주문이나 없는 주문은 404 `ORDER_NOT_FOUND`.
- 결제 금액이 0원(쿠폰으로 전액 할인)이면 `POST /mypage/buy` 에서 바로 `ORDER_COMPLETED` 이고 카드/계좌 입력 없이 끝납니다.
- 포인트는 현재 꺼져 있습니다 (`buy.POINTS_ENABLED=false`, RDS에 `users.point` 없음).

## 4. 결과 확인 위치

- DB: `orders.status` 가 `paid` 로 바뀌고, `enrollments` 에 강의가 추가되고, 장바구니에서 빠집니다. 쿠폰을 썼으면 `user_coupons.used=1`.
- 승인 기록(영수증): 서버 실행 폴더의 `./vpg/approvals.csv` (`vpg.ledger-path` 로 변경 가능). 영수증 화면의 승인번호(`VPG-…`), 카드 마스킹(`VISA ****1111`), 계좌(`은행 004 ****1234`)는 이 파일에서 읽습니다. DB에는 승인번호 컬럼이 없습니다.
- 서버는 시작할 때 CSV를 읽어 메모리에 올립니다. CSV를 손으로 고쳤다면 서버를 재시작하세요.

## 5. 다시 테스트하려면 (구매 초기화)

같은 강의를 다시 사려면 해당 사용자의 `enrollments`, `order_items`, `orders` 행을 지우고(쿠폰을 썼다면 `user_coupons.used=0`), 필요하면 `./vpg/approvals.csv` 의 해당 `merchant_order_id` 줄을 지운 뒤 서버를 재시작합니다.
